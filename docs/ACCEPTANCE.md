# Acceptance criteria: status and evidence

Each criterion from the specification (section 8), where it is implemented, and how it was
verified. "Live" means verified with running processes (browser, Celery worker/beat, SMTP),
beyond the automated test suite.

| # | Criterion | Status | Evidence |
|---|---|---|---|
| 1 | A user can securely log in and see only the websites permitted for their role. | ✅ | Argon2id, HttpOnly/Secure session cookie, CSRF, rate limits, lockout (`tests/test_auth.py`). The authorization matrix covers 81 routes × 6 actors, with a cross-tenant leak scan (`tests/test_permission_matrix.py`). Live: a second tenant probing the first got 404s and empty lists. Live in Docker over HTTPS: the session cookie is `Secure` and `HttpOnly`. |
| 2 | A developer can register a website and configure its monitoring schedule. | ✅ | Websites API and UI with 1–5 min intervals, retries, thresholds and crawl settings (`tests/test_websites.py`). Live in the browser as a developer. |
| 3 | Uptime checks run automatically even when nobody is logged in. | ✅ | Celery beat → dispatcher (`FOR UPDATE SKIP LOCKED`) → worker (`tests/test_stats_and_scheduler.py`). Live: real worker and beat, nobody signed in, status read straight from the database. In Docker, `/api/readyz` reports fresh worker and scheduler heartbeats. |
| 4 | Website downtime is detected, recorded, and reported. | ✅ | State machine: retries, then an incident, then one down and one recovered email (`tests/test_engine.py`). Live: stopping a site's process gave a confirmed incident and emails over real SMTP; restarting it gave a recovery email. |
| 5 | Monthly crawling identifies broken links and saves audit results. | ✅ | Crawler and 19 checks with coverage, issues tracked across runs, idempotent monthly scheduling (`tests/test_audit.py`, `tests/test_audit_api.py`). Live: the background worker audited a local site with known defects; the scheduler is idempotent. |
| 6 | Domain and SSL expiry information is retrieved where supported. | ✅ ⚠️ | RDAP (IANA bootstrap) with WHOIS fallback, and TLS certificate inspection (`tests/test_expiry.py`). Live against local RDAP/WHOIS stand-ins and a real TLS server. **Not verified against the public registries:** the build sandbox's network policy blocks them. Production needs outbound HTTPS to `data.iana.org` and the RDAP servers. |
| 7 | Hosting expiry can be recorded manually when automated retrieval is unavailable. | ✅ | Manual entry, always labelled "Manual entry (not verified)"; "Unknown" when absent. Provider adapter interface with encrypted credentials (no providers installed, as decided). |
| 8 | Monthly PDF reports are generated, saved, and downloadable by authorized users. | ✅ | Scheduled and manual generation, locked and checksummed, client publication, email with attachment (`tests/test_reports.py`). Live: generated by the worker in Docker and downloaded over HTTPS, then restored from backup and downloaded again. |
| 9 | The report includes uptime, audit findings, incidents, expiry information, and historical comparisons. | ✅ | Sections 1–5: availability, outages, response chart, audit and coverage, issues (new / fixed-verified / recurring / outstanding), domain/hosting/SSL with sources, maintenance performed, recommendations, comparison with the previous month. Verified by PDF text extraction in tests. |
| 10 | Clients cannot access technical logs, internal notes, or another client's data. | ✅ | Separate client response models; the matrix test's client-payload scan; client reports with no causes, internal notes, raw errors or account references; client PDFs use plain wording. ## Known limitations (documented, not hidden)
- **Monitoring location:** checks run from one location; a network problem between the server
  and a website is recorded as downtime.
- **JavaScript:** pages built in the browser by JavaScript are not rendered by the crawler, and
  each audit reports this as "not checked".
- **Hosting dates:** renewal dates are manual unless a provider integration is added (none ship
  by default).
- **Unicode in PDFs:** full coverage requires the `fonts-dejavu-core` package, which the Docker
  image installs by default.
- **Single-node design:** Redis and PostgreSQL run on the same host. For high availability, use
  managed PostgreSQL and Redis, and run several `worker` containers (beat must stay single).
